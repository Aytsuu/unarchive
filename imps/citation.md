# Citation and project versioning plan

Status: **approved and implemented**. Citations identify preserved versions using their version-specific public URLs. Existing records receive a clearly marked legacy baseline when migrated.

## Citation foundations and current gaps

A citation requires an accurate title, ordered authors, academic completion year, and institution; Unarchive is the repository. A thesis description is included when the project's type is known, and a version-specific URL is included when available. An abstract, publication date, project type, or URL does not prevent a citation from being generated. The academic completion year is the year of Date ended; it is never inferred from the Unarchive publication timestamp. The publisher is not automatically an author. Existing contributor names are unstructured and may include non-author contributors, so they need author confirmation and citation-ready formatting before a fully accurate APA reference can be guaranteed. Existing projects lacking verified metadata must not receive invented values.

The public project page and demo endpoints must be readable without an account for a citation URL to be useful. Citation URLs must come from a configured, trusted canonical app origin, not a request Host header. A localhost URL is useful only for development and is not publicly accessible. The current URL is mutable; citations point to the selected preserved version instead.

APA references for a repository thesis generally include author(s), completion year, title, a thesis description and institution, repository, and URL. The precise degree label, author name structure, and punctuation need verified metadata; don't fabricate them. References: [Monash University thesis guidance](https://guides.lib.monash.edu/apa-7/theses-and-dissertations) and [APA reference-list guide](https://apastyle.apa.org/instructional-aids/creating-reference-list.pdf).

## Approved immutable versions

1. **Version 1 on publication.** When a project is first published, create an immutable snapshot with version number 1, original publication timestamp, snapshot timestamp, ordered verified authors, title, academic completion year, institution, project type, abstract, other public project details, and exact demo asset references. Record the current version on the project. A version number is issued only when its snapshot is safely committed.
2. **Versioned public address.** Serve each frozen snapshot at `/projects/{projectId}/versions/{version}`. The existing `/projects/{projectId}` points to the latest public version. Copy Citation from a version page uses its version-specific URL and the approved version notation; confirm the final formatting against APA guidance rather than guessing. No versioned URL should silently redirect to a newer version.
3. **Edits create versions.** Provide an owner-authorized edit flow. A successful edit to citation or public project content creates a new snapshot and updates the current-version pointer. Use a compare-and-swap precondition based on the version the editor loaded; reject stale concurrent edits instead of losing changes. Retried submissions use an idempotency key so they cannot create duplicate versions. Views and stars remain separate mutable metrics and do not create versions.
4. **Atomic storage.** Use a `projectVersions` collection with a unique `(projectId, version)` index and commit snapshot insertion and the project pointer update in a MongoDB transaction. The current local stack uses standalone MongoDB and may disable transactions; enabling a replica set and testing the required local/production deployment changes is a prerequisite. Do not deploy a dual-write flow that can leave the pointer and snapshot out of sync. If a replica set is unavailable, stop and agree on a different atomic model before implementation.
5. **Legacy records.** Backfill one baseline snapshot from the metadata that actually exists when the backfill runs. Record its capture time and mark it as a legacy baseline; do not assert that missing authors, completion year, type, or earlier revisions were known. Make the backfill resumable and idempotent. A complete versioned APA citation is available only when the required metadata is verified.
6. **Assets and deletion.** Immutable versions retain their exact R2 demo keys. Do not overwrite an object used by an older version; retain it while any snapshot references it. Update cleanup/reset tooling to account for snapshot references. For withdrawal or sensitive corrections, use an explicitly defined takedown/tombstone flow so an address can communicate withdrawal without silently substituting different content; legal/privacy removal must remain possible. Document retention and removal decisions before release.
7. **Verification and rollout.** Test public anonymous reads, author-only writes, missing/incomplete metadata, exact author order and citation output, old version links after updates, concurrent edits, idempotent retries, transaction failures, legacy backfill, asset retention, tombstones, and reset tooling. Invalidate both current and version-related caches after successful writes. Establish monitoring, a backup and a rollback plan before any migration.

## Local migration and recovery

Back up MongoDB before converting an existing standalone database or capturing baselines. Restart the local stack to initialize its single-node replica set, then run `node --env-file=.env.local scripts/backfill-project-versions.mjs --apply`. The command is local-only, resumable, and idempotent; without `--apply` it does not modify records. Keep the backup in a protected location because it contains account data. Restore a backup only after stopping writes and following MongoDB's restore procedure. Retain old demo objects as long as snapshots reference them; project reset explicitly removes version records and their associated assets. A withdrawn project and its versions display a tombstone, while operators retain the ability to perform legally required removal.
